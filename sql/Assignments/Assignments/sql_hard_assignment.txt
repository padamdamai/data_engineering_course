1.) Tree Node Classification (Asked in Uber)

A company stores hierarchical data in a table where each row represents a node and its parent node.

Using this table, classify each node into one of the following categories:
	•	ROOT → Node with no parent
	•	LEAF → Node that does not have any child
	•	INNER → Node that has both a parent and at least one child

Write a SQL query to return each node along with its corresponding node type.

Table: tree

+------------------+----------+
| node             | INTEGER  |
| parent           | INTEGER  |
+------------------+----------+

•	node represents the current node
•	parent represents the parent of the node
•	The root node has parent = NULL

Example Input

+------+--------+
| node | parent |
+------+--------+
| 5    | 8      |
| 9    | 8      |
| 4    | 5      |
| 2    | 9      |
| 1    | 5      |
| 3    | 9      |
| 8    | NULL   |
+------+--------+

Expected Output

+------+-----------+
| node | node_type |
+------+-----------+
| 5    | INNER     |
| 9    | INNER     |
| 4    | LEAF      |
| 2    | LEAF      |
| 1    | LEAF      |
| 3    | LEAF      |
| 8    | ROOT      |
+------+-----------+
Explanation
	•	Node 8 has no parent → ROOT
	•	Nodes 5 and 9 have a parent and also act as parents for other nodes → INNER
	•	Nodes 1, 2, 3, 4 never appear as a parent → LEAF


CREATE TABLE medium_sql.tree (
    node   INT,
    parent INT
);

INSERT INTO medium_sql.tree (node, parent) VALUES
(5, 8),
(9, 8),
(4, 5),
(2, 9),
(1, 5),
(3, 9),
(8, NULL);

2.) Paytm Repeated Payments Detection (Asked in Paytm)

Sometimes in Paytm, a payment gets re-triggered due to network retries, app refresh, or gateway timeouts — causing a user to accidentally pay the same biller again with the same UPI handle for the same amount within a short window.

Using the paytm_transactions table, identify repeated payments and return the count of repeated payments.

Rules
	•	A payment is “repeated” if the same biller_id + same upi_id + same amount occurs within 10 minutes of the previous identical payment.  ￼
	•	Do not count the first transaction in a repeated group (only the “extra” ones are counted).  ￼

Table: paytm_transactions

+-------------------------+----------+
| transaction_id          | INTEGER  |
| biller_id               | INTEGER  |
| upi_id                  | INTEGER  |
| amount                  | INTEGER  |
| transaction_timestamp   | TIMESTAMP|
+-------------------------+----------+

 Example Input

+----------------+----------+--------+--------+------------------------+
| transaction_id | biller_id | upi_id | amount | transaction_timestamp |
+----------------+----------+--------+--------+------------------------+
| 1              | 901       | 11     | 499    | 2025-01-10 10:00:00    |
| 2              | 901       | 11     | 499    | 2025-01-10 10:07:00    |
| 3              | 901       | 11     | 499    | 2025-01-10 10:25:00    |
| 4              | 902       | 22     | 1200   | 2025-01-10 11:00:00    |
| 5              | 902       | 22     | 1200   | 2025-01-10 11:09:30    |
| 6              | 902       | 22     | 1300   | 2025-01-10 11:05:00    |
| 7              | 903       | 33     | 799    | 2025-01-10 12:00:00    |
+----------------+----------+--------+--------+------------------------+

Expected Output

+------------------------+
| repeated_payment_count |
+------------------------+
| 2                      |
+------------------------+

Explanation
	•	(Txn 1 → Txn 2): Same biller 901, same upi 11, same amount 499, within 7 minutes → Txn 2 is a repeated payment
	•	(Txn 2 → Txn 3): Same combo but 18 minutes later → not repeated 
	•	(Txn 4 → Txn 5): Same biller 902, same upi 22, same amount 1200, within 9m 30s → Txn 5 is repeated 
	•	Txn 6 differs in amount (1300) → not repeated
So total repeated payments = 2

SQL Setup

CREATE TABLE hard_sql.paytm_transactions (
    transaction_id         INT PRIMARY KEY,
    biller_id              INT,
    upi_id                 INT,
    amount                 INT,
    transaction_timestamp  TIMESTAMP
);

Each trip request can either be completed or cancelled by the traveler or the driver.

Write a SQL query to compute the daily trip cancellation rate for trips requested between Nov 1, 2024 and Nov 3, 2024, considering only trips where both the traveler and the driver are not banned.

	•	status = 'cancelled_by_traveler'
	•	status = 'cancelled_by_driver'
	•	Cancellation rate formula:

cancelled_trips / total_trips

	•	Round the cancellation rate to 2 decimal places
	•	Return results grouped by day

	•	'completed'

+----------+--------+------------+

	•	role can be:
	•	'traveler'
	•	'driver'
	•	'partner'
	•	Only users with banned = 'No' are considered valid
